## 使用方式

每题先用“参考回答”完成 30–90 秒回答，再根据追问展开。不要逐字背诵；把第一人称内容改成自己真实承担的工作。涉及线上效果时只报告实际测量过的数据，不编造 QPS、命中率或成本收益。

## 一、项目介绍与整体架构

### Q1：请用一分钟介绍这个项目

参考回答：

这是一个多租户企业知识库问答平台。用户在管理端创建知识库并上传文档，Java 服务把原文件保存到 S3 兼容存储，通过异步流水线用 Tika 解析、切分，再调用 Python 生成 Embedding 并写入 PostgreSQL pgvector。提问时，Java 负责 JWT 鉴权、租户隔离、会话和 Trace 持久化，Python 的 RagEngine 负责问题独立化、意图路由、知识库选择、查询改写、向量与关键词双路召回、RRF 融合、重排、上下文打包、LLM 生成和引用校验。前端使用 React，通过 REST 和 POST SSE 提供聊天及管理界面。

项目的重点不是只把向量检索接到大模型，而是补齐了入库失败恢复、权限隔离、检索调试、消融测评和执行追踪。当前会话记忆正在从 Java 向 Python 迁移，工作区契约还没有完全对齐，我会把它作为当前技术债说明，而不会说成已经稳定上线。

### Q2：这个项目解决什么业务问题？

参考回答：

通用大模型不了解企业内部制度、合同和操作手册，也无法给出可核查来源。项目把企业文档转成可检索 Chunk，在回答时限制模型使用选定租户和知识库的上下文，并返回文档/Chunk 引用。管理员还能看到入库任务、检索各阶段和 Trace，知道“是文档没解析、检索没召回，还是模型没有正确利用证据”。

### Q3：为什么使用 Java + Python 双后端？

参考回答：

边界按变化速度和生态划分。Java 承担稳定的企业业务：认证授权、租户、知识库、对象存储、任务状态、会话和持久化；Python 承担变化快的 AI 链路和模型适配。这样可以利用 Spring 的业务与事务能力，也能使用 Python 的 LangChain、模型 SDK 和数据评测生态。

代价是多一次网络调用和跨语言契约维护，所以项目为 Chat、Embedding、Summary、Retrieval Debug 和 Evaluation 定义了独立客户端与 DTO，并需要做超时、错误映射和 SSE 代理。若团队规模很小、业务简单且不需要 Java 生态，单体 Python 会更省维护成本。

### Q4：为什么 PostgreSQL 同时存业务数据和向量？

参考回答：

项目规模下，PostgreSQL + pgvector 可以让租户、知识库、文档、Chunk 和向量共享事务语义与过滤条件，降低引入独立向量数据库后的同步和运维成本。HNSW 提供近似向量检索，pg_trgm 支持关键词包含检索。

限制是当前向量列固定为 `vector(1536)`，维度不是动态的；数据和并发规模继续增长后，需要用实际延迟、召回率、索引构建成本和运维复杂度评估分区或迁移，而不是因为“向量数据库更专业”就直接更换。

### Q5：一次请求跨哪些组件？

参考回答：

浏览器把 Bearer Token 和问题交给 Java。Spring Security 校验 JWT，RequestContextFilter 建立用户、租户和 requestId 上下文。Java 创建或读取会话与用户消息，生成 traceId，再调用 Python。Python 完成路由、检索和生成，通过 JSON 或 SSE 返回。Java 保存助手消息与 Trace，再转给前端。RAG 检索阶段 Python 直接读共享 PostgreSQL，模型阶段访问外部 Embedding、Rerank 和 LLM 服务。

## 二、Java、认证与多租户

### Q6：JWT 登录方案如何设计？

参考回答：

Java 使用 Spring Security OAuth2 Resource Server 和 RSA 签名。Access Token 默认 15 分钟，Refresh Token 默认 7 天；刷新令牌在数据库持久化，可轮换和撤销。前端普通请求收到 401 后进行一次刷新，并用共享 Promise 避免多个并发请求重复刷新。

用户表有 tokenVersion，改密码或全设备退出时可以使旧 Access Token 失效。登录和刷新公开，其余业务接口默认认证；401 表示未认证或 Token 无效，403 表示身份有效但权限不足。

### Q7：为什么选 RSA，而不是所有服务共享 HMAC 密钥？

参考回答：

RSA 将签发和验证能力分离。持有私钥的认证服务才能签发，其他验证方只需公钥，降低验证服务泄漏后伪造 Token 的风险。当前主要由 Java 验证 JWT，但该方案便于后续服务只分发公钥。代价是密钥生成、轮换和文件权限更复杂，因此部署必须把密钥作为运行时秘密管理。

### Q8：多租户隔离在哪里实现？

参考回答：

身份从 JWT 恢复到 CurrentUserProvider，而不是信任前端传入 tenantId。业务 Service 在访问知识库、文档、任务和 Trace 时校验目标租户；TenantAccessGuard 允许平台管理员跨租户，普通用户和租户管理员只能访问自己的租户。Python 查询也在 SQL 中显式带 tenant_id 和 deleted 条件。

风险点是 MyBatis 逻辑删除并不自动解决所有租户隔离，原生 SQL 更不会自动加条件。测试要创建两个租户和同名/相似 ID 资源，覆盖查询、更新、删除和 SSE，而不是只测列表接口。

### Q9：PLATFORM_ADMIN、ADMIN、USER 有什么区别？

参考回答：

PLATFORM_ADMIN 负责平台级租户管理，并可在实现允许的地方跨租户；ADMIN 管理本租户用户、知识库、文档、模型、任务、测评和 Trace；USER 主要使用聊天、可用知识库和模型查询。后端通过 `@PreAuthorize` 与资源级检查共同保证权限，前端 AdminRouteGuard 只是用户体验，不能替代服务端授权。

### Q10：RequestContextFilter 有什么作用？

参考回答：

它在 Bearer Token 认证之后，从 SecurityContext 建立 LoginUser、tenantId 和 requestId，并写入 MDC，供 Service、日志和 Trace 使用。它被禁止作为普通 Servlet Filter 自动注册，避免执行两次或在认证前执行。

异步任务不会自动继承 ThreadLocal，所以入库监听器显式恢复用户和 requestId，并在 finally 清理，防止线程池复用导致上下文串号。

### Q11：统一异常和响应有什么价值？

参考回答：

Java 普通接口统一返回 ApiResult，字段为 success、code、message、data、timestamp；全局异常处理器把客户端错误、业务错误、数据库错误和远程错误映射成稳定状态。前端可以统一解包和展示，服务日志保留底层原因。

但 SSE 不能套普通 JSON 外层，错误要作为 event:error 放在流内；Python 的 Pydantic 422 和 HTTPException 也不总是 ApiResult 格式，所以跨服务客户端必须先判断 HTTP 状态，再解析业务体。

## 三、文档上传与入库

### Q12：文档入库链路如何设计？

参考回答：

上传服务先校验知识库和文件，清理文件名，读取字节并计算 SHA-256，然后把原文件写到 S3。短事务登记文档、入库任务、步骤和知识库配置快照，事务提交后发布事件。异步流水线执行 PARSE、EMBED、COMPLETE：解析阶段下载文件、Tika 提取、清洗和切分并写 Chunk；Embedding 阶段分批调用 Python 并写 pgvector；完成阶段更新文档 READY 和任务 SUCCESS。

上传 HTTP 返回只代表登记成功，前端通过任务接口观察最终状态。

### Q13：如何处理重复上传？

参考回答：

内容使用 SHA-256，而不是只看文件名。同一租户、知识库、有效文档范围内有部分唯一索引。服务先查询已有记录，减少不必要上传；并发情况下仍以数据库唯一约束兜底。若数据库登记失败，服务尽力删除刚上传的独立对象；如果检测到并发重复，则清理新对象并返回已有文档。

批量上传是逐文件处理，不是整个批次一个事务，后一个文件失败时前面的文件可能已成功。客户端可依赖内容幂等安全重试。

### Q14：大文件会不会 OOM？

参考回答：

当前实现调用 `MultipartFile.getBytes()`，为复用同一份数据做哈希和上传，会把整个文件读入 JVM 内存。虽然单文件限制 100MB，但多个并发大文件仍可能造成明显堆压力。所以不能回答“已经完全流式，不会 OOM”。

优化可以把流写入受控临时文件，一边计算摘要一边上传，或使用支持重开/分段的流；同时限制上传并发、请求体大小和临时磁盘配额。优化前要保证哈希幂等与 S3 失败补偿语义不变。

### Q15：为什么保存 pipeline_config 快照？

参考回答：

知识库的 chunkStrategy 是后续任务默认配置，任务创建时把 chunkType、大小、重叠、Embedding 模型/维度/批次保存到 ingestion_task.pipeline_config。这样任务执行或重试期间即使管理员修改知识库配置，同一个任务仍使用原参数，便于复现和审计。

### Q16：为什么把入库拆成多个阶段和事务？

参考回答：

解析和模型调用都可能很慢，如果用一个大事务，会长期占用连接并扩大回滚范围。分阶段、分批持久化让任务状态可见，失败时能从 PARSE 或 EMBED 恢复，并保留已经成功的向量批次。

代价是系统允许中间状态，不能依赖单个数据库事务保证全链路原子性。每个步骤要幂等，状态更新、失败记录和重试策略必须明确。

### Q17：任务失败后如何恢复？

参考回答：

只有 FAILED 任务允许重试。系统读取首个失败的细粒度 stepCode：上传、解析、切分或保存失败从 PARSE 开始；Embedding 或向量索引失败从 EMBED 开始。它重置本次需要执行的步骤、清除错误并在事务提交后重新发布事件。

事件和线程池都在进程内，进程崩溃可能留下 PENDING/RUNNING，目前不能声称有持久 MQ 的自动恢复。生产化可以增加超时扫描、租约和持久队列。

### Q18：支持哪些解析和切分策略？

参考回答：

Apache Tika 负责多格式文本提取；TextNormalizer 清理文本，TextChunkerFactory 提供 recursive、paragraph、fixed 三种策略。默认 recursive，目标 800 字符、重叠 100 字符。长度是字符，不是 Token。

当前没有 OCR 和视觉版面理解，扫描 PDF、图片文字和复杂表格不能保证质量。遇到召回差，应先检查解析结果和 Chunk，再调 topK 或模型。

## 四、RAG、意图与检索

### Q19：RAG 完整流水线是什么？

参考回答：

先把多轮问题改写成独立问题，再做意图路由。KNOWLEDGE 意图进入知识库选择；选择明确后生成语义查询、关键词、同义词和替代查询，执行向量与关键词召回，RRF 融合，Cross-Encoder 重排，再按字符预算打包上下文。存在证据才调用 LLM，最后校验引用。

CHAT 可跳过检索直接生成；TOOL 执行已注册工具后把结果交给模型；知识库不明确或工具不可用会澄清；无检索依据直接返回 NO_EVIDENCE，避免无证据生成。

### Q20：问题独立化和查询改写有什么不同？

参考回答：

问题独立化解决多轮语境，例如把“它的上限呢？”改成脱离历史也能理解的问题。查询改写面向检索，将独立问题拆成 semanticQuery、keywords、synonymKeywords 和 alternativeQueries。前者保持用户意图，后者优化召回。混在一起会导致难以判断改写究竟改善了上下文理解还是检索覆盖。

### Q21：意图路由如何工作？

参考回答：

先走规则路由，能确定的 CHAT、CLARIFY、显式知识库等直接短路；fallback 时把 LLM 分类和向量意图匹配放在线程池并行执行，再按权重和置信区间融合。任何一路失败可由另一路兜底。L0 是 CHAT、KNOWLEDGE、TOOL、CLARIFY，L1 domain 用于选择 EXPENSE、HR、CONTRACT、POLICY 或 GENERAL 知识库。

多轮独立化后可继承上一轮 route，但上一轮 CLARIFY 不继承。目前这依赖 lastRoute 契约，正处于会话迁移未完成状态。

### Q22：关键词检索用的是 BM25 吗？

参考回答：

不是。当前 KeywordRetriever 使用 PostgreSQL `ILIKE` 对 Chunk 内容和文件名做包含匹配，pg_trgm GIN 索引用于加速；正文每个关键词命中加 1，文件名命中加 2。它会去空去重、过滤少于两个字符的词，最多取 6 个，并转义 LIKE 特殊字符。

历史材料中的 BM25 是旧表述。若要升级 BM25，应新增 PostgreSQL 全文检索或外部搜索实现，并通过同一数据集做消融对比。

### Q23：向量检索怎么保证模型空间一致？

参考回答：

指定知识库时，PgVectorRetriever 从 chunk_strategy 读取 embeddingModel 和 embeddingDimension，用相同配置生成查询向量，并在 SQL 中过滤 Chunk 的模型和维度。Java 入库也保存这两个标记。

不过数据库列仍是 `vector(1536)`，Python Embedding HTTP 请求目前只有 texts 和 model，没有 dimension 字段，所以“任意维度动态切换”还没完成。生产配置必须确保模型输出、Python 默认、Java 校验和数据库列一致。

### Q24：RRF 是什么，为什么使用它？

参考回答：

RRF 根据排名而不是原始分数融合。一个候选在每个来源的贡献近似为 `weight / (k + rank)`，项目默认 k=60，再把多路贡献累加。向量余弦分数和关键词命中分数不在同一量纲，直接加权原始值需要校准；RRF 更稳健，也能奖励多路同时命中的结果。

它的局限是忽略原始分数间距，k 和权重仍需用数据集评估。RRF 不能弥补文档未解析或正确 Chunk 根本没有召回的问题。

### Q25：为什么还需要 Rerank？

参考回答：

第一阶段检索追求高召回，候选数量较多；RRF 只融合排名。Cross-Encoder 同时看问题和候选文本，计算更细的相关性，把最有用的少量 Chunk排到前面。这样可以减少送入 LLM 的噪声。

重排更慢且有额外模型成本，因此只处理 fusionTopK 候选，支持关闭和降级，并单独记录耗时。效果要比较 HYBRID 与 HYBRID_RERANK，而不是凭主观判断。

### Q26：上下文为什么要做预算打包？

参考回答：

即使重排后的内容相关，也不能无限塞入 Prompt。ContextPacker 按总字符数和单文档字符数截断，保留实际进入上下文的文档，生成 citationIndex 和 contextTruncated。这样控制模型窗口、延迟和费用，并保证引用来自真实提供的证据。

字符预算只是近似；若模型切换或中英文比例变化，可以升级为按目标 tokenizer 预算，并为系统提示、历史和输出预留空间。

### Q27：怎么降低幻觉？

参考回答：

系统在链路上做三层约束：知识库和租户过滤保证证据范围；无证据时跳过 LLM 返回 NO_EVIDENCE；生成后校验引用序号，记录有效和无效引用。Trace 保存模型输入摘要、检索数量与后处理结果，便于定位。

这只能降低风险，不能证明答案事实完全正确。还需要基于事实样本做忠实度和完整性评估，而当前九组测评主要衡量检索，不是完整回答质量。

### Q28：工具调用如何保证安全？

参考回答：

当前只有注册表中的 calculator。参数由路由结构化成字典，计算器先做字符白名单，再用 Python AST 递归解释允许的数字、四则、取模和幂运算，不调用 eval，也不允许名称、属性和函数调用。未注册或执行异常进入澄清。

还需要补充表达式长度、数字范围、幂指数和执行资源限制。Schema 里出现 web_search 只是示例，不能说项目已接入搜索工具。

## 五、SSE、会话、并发与一致性

### Q29：为什么选择 SSE，而不是 WebSocket？

参考回答：

聊天主要是客户端发起一次请求、服务端持续返回文本，是单向流。SSE 语义简单，能经过普通 HTTP 基础设施，前端用 fetch POST 携带 JSON 和 Authorization，Java 用 SseEmitter 代理 Python 流。

WebSocket 更适合持续双向事件。这里使用 fetch 而不是原生 EventSource，是因为需要 POST 请求体和认证头。代理必须关闭缓冲、增加读超时，并正确传播取消。

### Q30：SSE 有哪些事件？前端如何判断成功？

参考回答：

典型顺序是 start、route、retrieval、多个 delta、final、done；异常时可能是 start、error、done，Java 也能转发 heartbeat。delta 是实时草稿，final 才包含最终回答、引用、状态和 Trace。done 只说明流结束，不能单独作为业务成功；流结束而没有持久化 final 应视为异常。

### Q31：客户端断开时发生什么？

参考回答：

前端 AbortController 中止 fetch；Java 的流会话应停止读取上游并记录关闭原因；Python 生成器捕获 GeneratorExit，TraceRecorder 标记失败。由于用户消息可能已经在调用 Python 前保存，断开不等于本轮没有数据库记录，重试和 UI 展示要避免重复消息。

### Q32：会话记忆如何设计？现在完成了吗？

参考回答：

现有 Java 方案用数据库保存完整消息，Redis List 缓存最近消息，摘要达到消息数或估算 Token 阈值后异步调用 Python，把摘要写到 chat_conversation，并裁剪工作记忆。Redis TTL 是 24 小时，数据库是回退来源。

但当前工作区在迁移会话写入所有权到 Python：ChatRequest 已删除 history/summary/lastRoute，ChatService 仍读取这些字段；ChatData 新增必填 conversationId 但组装未提供；PostgresConversationStore 的部分方法缩进错误，并引用尚未创建的 chat_turn。因此准确说法是“Java 方案和迁移代码都存在，迁移尚未完成”，不能说 Python 记忆已上线。

### Q33：如何防止会话并发串号？

参考回答：

路由状态不能存在进程单例字段中，应按 conversationId 持久化 last_route，并同时校验 tenantId 和 userId。异步线程要恢复并清理上下文。进一步需要定义同一会话是否串行执行，或者使用 version/turn 表做乐观并发和 requestId 幂等。

当前迁移计划引入 chat_turn，但迁移表尚不存在，所以这仍是需要完成和测试的部分。

### Q34：Java 事务能覆盖 Python、S3 和模型调用吗？

参考回答：

不能。数据库事务只覆盖当前数据库连接。S3 上传采用补偿删除；入库用任务状态、幂等步骤和重试实现最终一致；聊天在远程调用前后使用短事务保存状态和结果。外部调用失败要记录可诊断状态，而不是期待数据库 rollback 撤销外部行为。

如果需要更强保证，可以使用 Outbox、持久队列、幂等键和状态机，而不是引入跨服务两阶段提交。

## 六、测评、可观测与性能

### Q35：如何证明检索优化有效？

参考回答：

项目提供九组消融实验，分别组合 VECTOR、KEYWORD、HYBRID、RERANK、REWRITE 和 MULTI_QUERY。基础四组关闭 Rewrite，避免多个变量一起变化。指标包括 Hit@1/3/5/8、MRR、证据样本 ChunkHit@5、平均延迟、P95、失败和降级数量。

比较时固定语料、知识库、模型、topK 和数据集版本。当前指标证明的是检索效果，不等同于最终回答正确率。

### Q36：Hit@K 和 MRR 分别反映什么？

参考回答：

Hit@K 只关心前 K 个里是否出现正确文档，反映召回覆盖；MRR 取第一个正确结果排名的倒数并平均，更关心正确结果是否靠前。例如正确结果排第 1，RR 是 1；排第 4，RR 是 0.25；没命中是 0。两者结合可以区分“能找到但排名低”和“根本找不到”。

### Q37：Trace 如何设计？

参考回答：

RagEngine 为 QUERY_RESOLVE、QUERY_ROUTE、KNOWLEDGE_BASE_SELECT、RETRIEVAL_QUERY_REWRITE、HYBRID_RETRIEVE、RERANK、CONTEXT_PACK、LLM_GENERATE、ANSWER_POST_PROCESS、TOOL_EXECUTE 建节点，记录状态、耗时和输入输出摘要。短路步骤记录 SKIPPED 和原因。Java 把 Trace 存到 rag_trace，管理端提供列表、统计和详情。

requestId 关联 HTTP 日志，traceId 关联问答执行，taskId 关联入库，不应混用。Trace 可能包含问题和内容摘要，必须按租户授权并控制敏感数据。

### Q38：有哪些监控指标？是否已有完整监控平台？

参考回答：

Java 用 Micrometer 记录入库任务创建/完成、任务耗时、步骤完成/耗时和 Embedding 批次耗时，Actuator 暴露 health/info/metrics。数据库任务和 Trace 还提供可持久查询的业务统计。

仓库没有完整的 Prometheus、Grafana 或 OpenTelemetry 部署，因此应说“已有埋点和查询基础”，不能说“完整告警平台已经上线”。

### Q39：系统的主要性能瓶颈在哪里？

参考回答：

入库侧包括大文件内存读取、Tika 解析、Embedding 批次和数据库向量写入；查询侧包括问题独立化/改写、并行召回、Rerank、LLM 首 Token 和 SSE 长连接。连接池也受 Java、Python 进程数和线程池共同影响。

优化前先看分阶段 Trace、P95 和失败率。常见手段是减少不必要模型调用、合理批次与候选数、缓存稳定结果、限制并发、配置超时降级。不能只扩大线程池，因为可能把压力转移到数据库和模型配额。

### Q40：如何水平扩展？

参考回答：

Java 的 JWT 无 Session 适合多实例，但入库事件在本地线程池，需要持久任务领取机制；Python 检索大体无状态，但当前测评 `_jobs` 在单进程内存，多个实例查询不到彼此作业；会话 Python 化也尚未完成。同一数据库的连接总量是实例数乘每实例池大小。

扩展顺序应先外置测评/任务状态、定义幂等和租约、完成会话唯一写入方，再增加实例，并验证 SSE 代理和连接池容量。

## 七、前端与工程质量

### Q41：前端如何处理 Java Long 精度？

参考回答：

Snowflake BIGINT 可能超过 JavaScript 的 `Number.MAX_SAFE_INTEGER`。Axios 和 SSE 都通过 json-bigint 按字符串解析 ID，TypeScript 类型也应保持字符串。不能在页面用 Number 或 parseInt 后再发送，否则可能访问错误资源。

### Q42：前端如何处理 Token 并发刷新？

参考回答：

请求拦截器附加 Access Token。非认证接口收到 401 后标记 `_retry`，所有同时失败的请求共享一个 refreshing Promise；刷新成功更新存储并重放原请求，失败清理 localStorage/sessionStorage 并跳转登录。这样避免多个请求同时轮换 Refresh Token 相互覆盖。

### Q43：当前自动化测试是否充分？

参考回答：

Python 有 Embedding API、Chat Stream、SSE、Trace、RRF、意图和回答后处理测试。前端有 typecheck、lint、build，但没有 test 脚本；Java 当前没有 src/test。因此单元覆盖不完整，尤其缺跨租户授权、Flyway、S3/数据库入库和 Java-Python 契约集成测试。

我会优先补高风险边界测试：跨租户/跨用户、重复并发上传、失败恢复、向量维度、SSE 无 final、会话迁移和评测重启，而不是只给简单 Getter/Controller 写形式化测试。

## 八、缺陷、取舍与开放题

### Q44：请指出当前项目三个真实技术债

参考回答：

第一，会话记忆迁移中 Java/Python Chat Schema、持久化和数据库表不一致，当前属于阻塞问题。第二，Redis 与摘要配置放在 rag.security 下，但代码分别绑定 rag.redis 和 rag.summary，配置注释与实际生效不一致。第三，异步入库和测评使用进程内线程池，缺少持久作业、租约和重启恢复。

此外，Embedding 默认写 mock 但没有实现 Mock 分支，向量列固定 1536，Java 缺测试，监控只到基础埋点。这些问题应按正确性、安全隔离、可恢复性、测试和性能顺序处理。

### Q45：如果让你继续开发，优先做什么？

参考回答：

先完成会话迁移：决定唯一写入方，统一请求/响应字段，补 chat_turn 或删除相关设计，完成请求幂等和同会话并发策略，并覆盖同步/SSE/旧数据/失败。随后修正配置前缀和健康检查，再补 Java-Python 契约与跨租户集成测试。最后把入库和测评状态外置，增加可恢复任务，再做 OCR、独立向量库等能力扩展。

这个排序先解决不能正确运行和可能越权的问题，再解决可靠性，最后做功能增强。

### Q46：如果检索质量差，你如何系统排查？

参考回答：

从上游到下游逐层排查：原文件是否存在 → Tika 文本是否正确 → Chunk 是否语义完整/重复 → 向量模型与维度是否一致 → tenant/knowledgeBase/deleted 过滤是否正确 → 向量与关键词各自是否命中 → RRF 是否把正确项融合出来 → Rerank 是否误降 → ContextPacker 是否截掉 → Prompt 和引用后处理是否正确。

使用调试接口和消融实验固定变量，不直接靠修改 Prompt 掩盖召回问题。

### Q47：如果数据量增长十倍，你会怎么演进？

参考回答：

先用真实数据测索引大小、检索 P95、写入放大、连接数和租户热点。数据库侧可考虑按租户/知识库分区、离线重建 HNSW、冷热数据和读写隔离；任务侧使用持久队列、租约、限流与批次背压；模型侧做请求批处理、缓存和供应商限流；S3 生命周期管理原文件。

只有 pgvector 已成为明确瓶颈时，再用同一接口评估专用向量库，并设计双写、回填、校验和切换方案。

### Q48：如何评价这个项目“企业级”的程度？

参考回答：

它具备企业应用常见的多租户、JWT、Refresh Token、权限、Flyway、对象存储、任务状态、失败重试、Trace 和测评基础，比单纯 RAG Demo 完整。但“企业级”还要求稳定部署、备份恢复、审计、安全测试、容量验证、持久任务、完整监控和 SLO，这些并未全部落地。

因此更准确的表述是“按企业应用边界设计并实现了主要骨架和核心链路，仍有生产化工作”。

### Q49：这个项目中最值得讲的设计取舍是什么？

参考回答：

我会讲两点。第一，用 PostgreSQL + pgvector 把业务过滤和向量检索放在一起，以更低复杂度换取当前规模下足够的检索能力，同时明确 1536 维和未来扩容限制。第二，把入库和 RAG 分为可观察阶段，允许短路、降级和重试，以最终一致性换取远程模型调用下的可恢复性。

回答取舍时同时讲收益、代价和触发重新评估的条件，比只列技术名更有说服力。

### Q50：你如何证明自己真正理解而不是只会调用框架？

参考回答：

我能从数据和故障路径解释系统：为什么向量和关键词分数不能直接相加、RRF 的 rank 公式、HNSW 与维度约束、SSE final/done 的业务差异、ThreadLocal 为什么会在线程池串号、外部调用为什么不能被本地事务回滚、部分唯一索引如何解决并发重复，以及测评作业为什么不能直接多 worker。

同时我会主动说明当前代码缺陷和验证边界。能解释失败条件、观测证据和修复顺序，比背诵“用了哪些技术栈”更能说明掌握程度。
